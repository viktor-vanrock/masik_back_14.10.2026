# Доменный контракт: правила текущей версии

Это описание **работающих сущностей после разделения**, а не проект будущего execution-сервиса. Согласованные ответы ML-инженера отделены от технических ограничений. Актуальность: 16.09.2026.

Для знакомства без кода: [обзор](project-overview.md). Для конкретных действий: [процессы](business-processes.md).

## 1. Модель без будущего Run

```text
Benchmark Service                         Catalog
Benchmark                                 MetricDefinition
└── Test                                  Model
    ├── описание и инструкции             MetricResult: Test ID + Metric ID + Model ID + число
    ├── внешние UUID Metric ─────────────► MetricDefinition
    ├── внешние UUID справочников ───────► справочники
    └── DatasetSubsample[]                CatalogEntry: Test ID + автор + модерация

Связи между сервисами — значения ID и сообщения, не SQL foreign key.
```

| Термин | Что это | Где живёт |
| --- | --- | --- |
| Benchmark / BenchmarkSuite | Группа связанных Test | Benchmark Service |
| Test / BenchmarkTest | Одно конкретное испытание в одной группе | Benchmark Service |
| DatasetSubsample | Принадлежащая Test часть данных для описания/визуализации | В описании Test |
| Metric / MetricDefinition | Независимое определение измеряемого показателя | Каталог |
| Model | Запись о модели, для которой получены результаты | Каталог |
| MetricResult | Готовое число для Test, Metric и Model | Каталог |
| CatalogEntry | Авторство и решение показать Test в каталоге | Каталог |
| Projection | Копия исходного объекта для чтения | Каталог |

`metrics` в HTTP-форме каталога — названия метрик. Каталог находит определения по имени, а отсутствующие создаёт с настройками по умолчанию; затем сохраняет `metricIds` в спецификации источника. Отдельной таблицы межсервисных назначений TestMetric сейчас нет. Опечатка в имени может создать лишнее определение, поэтому специальные метрики лучше заранее завести с правильной шкалой.

## 2. Benchmark

- Это группа, а не запуск и не численный результат.
- Test принадлежит ровно одному Benchmark.
- Нельзя удалить группу с активными Test.
- Названия группы проверяются на уникальность, включая конфликты с мягко удалёнными объектами.
- Группы сами не имеют статуса `published`: это решение о карточке Test в каталоге.
- Список активных Benchmark может содержать группу без публичных Test.

## 3. Test

Test описывает испытание, но не исполняет его:

| Блок | Содержимое |
| --- | --- |
| Идентификация | suiteId, name, nameEn |
| Объяснение задачи | description, shortDescription, taskDescription, instructions |
| Классификация | UUID справочников, skills, abilityTags |
| Данные | Размеры, распределения длин, примеры, DatasetSubsample, внешние ссылки |
| Проверка ответов | evaluationLogic, назначенные metricIds |
| Сравнение с человеком | humanBaseline и пояснение |
| Внешняя интеграция | Настройки GigaMetrics, ссылки на код |
| Происхождение | isGenerated, Jira и время генерации, если они известны |

Полный набор данных хранится вне каталога и источника. URL и команда запуска в карточке — сведения для внешнего исполнителя; эти сервисы не выполняют сохранённую shell-команду.

`evaluationLogic` находится **в Test**, а не Metric и не связи Test–Metric. Настройки GigaMetrics также принадлежат Test.

Черновик может пока не иметь Metric. Публикация и приём результата требуют хотя бы одну назначенную Metric; каталог не позволяет очистить их у уже опубликованного Test. Проверка «можно запустить Test» здесь не реализована, потому что запусков здесь нет.

Test с результатами пока нельзя менять на месте и удалять. Каталог запрещает свои операции сразу; источник применяет техническую блокировку по команде первого результата. Самостоятельный клиент источника обязан сообщать о своих внешних результатах/неизменяемости через API блокировки: источник не видит чужую БД результатов.

## 4. DatasetSubsample

Канонический термин — **DatasetSubsample**. API использует `datasetSubsamples`.

- Принадлежит одному Test; не является отдельным переиспользуемым Dataset.
- Не имеет собственных taskType/domains/subdomains, отличающихся от Test.
- Не получает MetricResult.
- Не выбирается как единица выполнения: это описание состава Test.
- Не обновляется и не версионируется независимо.
- При частичном PATCH Test не должен исчезать только из-за отсутствия поля в запросе.
- При редактировании существующей части передаётся её прежний ID; обычное изменение не пересоздаёт идентификаторы всех частей.
- Повтор ID в одном описании и ID, занятый другой частью другого Test, запрещены.

Источник хранит содержимое в JSON и отдельные занятые идентификаторы для проверки принадлежности. При удалении части из описания её запись идентичности также убирается; это не бессрочный исторический реестр UUID.

## 5. Metric и назначения

Metric существует независимо от Test. Разные Test выбирают разные наборы из общего справочника метрик.

- Для неназначенной Metric результат не принимается.
- Приём результата не дописывает назначение автоматически.
- Нельзя удалить использованную Metric: учитываются результаты, назначения в сохранённых копиях Test и ожидающие команды.
- Внутренние FK защищают ссылки результатов на Metric/Model, а назначения Test находятся в другом сервисе и защищаются проверками каталога, не cross-DB FK.
- У неиспользованной Metric удаление **физическое**, в отличие от мягкого удаления Benchmark/Test.
- Разные Metric показываются отдельно. Единого суммарного score для них нет.

В коде Metric уже имеет `priority`, `direction`, `minValue`, `maxValue`, `targetValue` и `metadata`. Это существующие технические настройки определения Metric. Ответ ML-инженера не вводил новые настройки связи Test–Metric; документация их не придумывает.

`higher_is_better` означает «больше — лучше», `lower_is_better` — «меньше — лучше». При создании/изменении определения проверяется minValue ≤ maxValue. Текущий API результатов не проверяет value на попадание в этот диапазон, а targetValue не включает автоматическую приёмку качества. Не следует менять шкалу существующей метрики ради одной карточки, не оценив влияние на другие Test.

Metric API не принимает содержательные значения `evaluationLogic` и `requiredGigaChatQualityLevel`: эти поля относятся к Test.

## 6. Результат и human baseline

Текущий результат относится напрямую к **Test + Model + Metric**. Он содержит число, при необходимости исходную строку, время получения и сведения об импорте.

- Результат только для Test целиком, не для DatasetSubsample или Benchmark.
- ModelVersion и Run не реализованы.
- `runId`, `subsetId`, `subsampleId` с непустыми значениями отвергаются API, а не включают скрытый режим.
- Строки импорта могут содержать исходное название части данных для диагностики. Это не поддержка результатов уровня части.
- human baseline — отдельное поле Test, допустимое по ответу ML-инженера.
- Специальная Model `human` не используется как обход этого правила.
- Число результата и поисковый score рекомендации — разные вещи.

## 7. Классификация

| Справочник | Человеческий смысл | Ограничения |
| --- | --- | --- |
| MacroGroup | Крупная группа способностей | Один выбранный родитель |
| SubGroup | Более узкая группа | Все выбранные дочерние группы принадлежат выбранному MacroGroup |
| AbilityTaxon | Конкретная способность | Независимый набор значений |
| TaskType | Тип задачи | Например, формат испытания |
| Modality | Вид информации | Например, текст |
| Language | Язык | Одно выбранное значение |
| Difficulty | Сложность | Справочное описание, не автоматически рассчитанная оценка модели |
| Capability | Требуемая возможность/режим | Набор значений |
| Domain | Предметная область | Набор значений |
| Subdomain | Более узкая область | Родитель каждой выбранной подобласти входит в domainIds |

Справочники принадлежат каталогу. Источник хранит внешние UUID без названий и без доступа к каталогу. Каталог проверяет существование, активность и родительские связи перед командой. Удаление используемого значения защищено, в том числе когда ссылка ещё только находится в ожидающей команде.

`skills` и `abilityTags` — свободные текстовые метки, не заменяют иерархию справочников.

## 8. Публикация не принадлежит Test

CatalogEntry содержит автора, проверяющего, причину отказа, время и статус:

- `validation` — ожидает проверки.
- `published` — разрешён публичный показ.
- `rejected` — отклонён, автор должен видеть причину.

В ответе карточки `validationStatus` может присутствовать как объединённое поле **для показа**. В источнике этого свойства нет; через PATCH Test менять его нельзя.

Удаление источника и архивация CatalogEntry — отдельные признаки. У опубликованной записи не будет публичной карточки, если исходный Test или Benchmark удалён.

## 9. Редакция — не полноценная версия испытания

`aggregateVersion` растёт при изменениях исходного объекта и помогает:

1. Отклонить запись по устаревшим данным.
2. Не применить старое Kafka-событие поверх нового.
3. Согласовать подтверждение операции.

Это не TestVersion с сохранённой историей спецификаций для воспроизводимости. Ни версия модели, ни seed, ни параметры реального выполнения в отдельной сущности запуска сейчас не сохраняются.

## 10. Что оставлено на будущее

Run, ModelVersion, полное версионирование Test, выполнение оценок и учёт параметров воспроизводимости — отдельный будущий функционал. Они **не входят** в результат текущего разделения и не являются требованием локального запуска.

Решения ML-инженера о возможном будущем Run не превращены в текущие таблицы/маршруты. Для понимания этой версии их изучать не нужно.
