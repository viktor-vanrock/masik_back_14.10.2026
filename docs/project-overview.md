# Проект для человека без ML-бэкграунда

Эта глава объясняет продукт, а не способы разработки нейросетей. Её можно читать отдельно от кода. Описана текущая версия двух бэкендов на 16 сентября 2026 года.

## 1. Какую проблему решаем

Языковая модель умеет отвечать на вопросы, писать текст или код, выбирать инструменты и выполнять многошаговые задачи. Но утверждение «эта модель хорошая» само по себе мало что говорит. Модель может хорошо писать текст и плохо решать арифметические задачи; справляться с простым вопросом и терять важную информацию в длинном диалоге.

Нужны конкретные испытания, которые проверяют определённое умение по понятным правилам. Такие испытания обычно называют бенчмарками.

Наш каталог помогает ответить на вопросы:

- Какие испытания уже есть?
- Что именно проверяет каждое из них?
- На каком языке и в какой области используются задания?
- Где лежат данные, примеры и код проверки?
- Какие показатели используются для оценки?
- Какие результаты уже были загружены для моделей?
- Что подходит под мою задачу и что делать, если подходящего испытания нет?

При этом сам каталог **не вычисляет качество модели**. Он хранит описания, помогает выбирать и показывает сохранённые результаты. Исполнение испытаний — другая задача.

## 2. Аналогия с экзаменами

Представьте систему учебных экзаменов:

- **Benchmark** — сборник экзаменов.
- **Test** — один конкретный экзамен из сборника.
- **Полные данные Test** — все экзаменационные задания; они находятся во внешнем хранилище.
- **DatasetSubsample** — описанная часть заданий внутри этого экзамена; она помогает понять его состав.
- **Metric** — правило, по которому измеряется результат: например, доля точно правильных ответов.
- **MetricResult** — уже полученное значение этого показателя для участника, то есть для модели.
- **CatalogEntry** — разрешение показать описание экзамена в публичном каталоге.

Эта аналогия объясняет роли объектов. Она не означает, что в проекте есть пользователи-ученики или онлайн-сдача экзаменов.

## 3. Почему названия раньше путались

Слово «тест» используется в двух разных смыслах:

1. **Предметный Test** — испытание модели, например GPQA Diamond.
2. **Автоматизированный тест проекта** — проверка нашего программного кода, например что неопубликованную карточку нельзя получить через публичное API.

Когда в этой документации написано Test с большой буквы, речь о первом смысле. Когда написано «юнит-тест» или «e2e-тест», речь о проверке программного обеспечения.

Слово «датасет» тоже неоднозначно. В разговоре ML-разработчик может назвать конкретный Test датасетом, потому что его основа — набор заданий. Но отдельной самостоятельной сущности Dataset в текущем контракте нет. Есть **Test с внешними данными** и принадлежащий ему **DatasetSubsample**.

Слово «бенчмарк» в UI может означать карточку. Однако в бэкенде карточка — это Test, а Benchmark — группа карточек. Это различие важно при поиске контроллеров, выборе `testId` и работе с БД.

Пример из нашего исходного набора:

```text
Benchmark: GPQA (Graduate-Level Google-Proof Q&A)
└── Test: GPQA Diamond

Benchmark: MERA Text
├── Test: ruMMLU
├── Test: ruHumanEval
└── другие Test этой группы
```

Всего в стартовом JSON — 10 групп и 40 Test. «40 бенчмарков» на главной странице — количество Test, не число групп.

## 4. Что лежит в карточке Test

Карточка — описание испытания. В ней могут быть:

| Информация | Зачем нужна |
| --- | --- |
| Название и описание | Быстро понять назначение испытания |
| Краткое описание и описание задачи | Увидеть суть без чтения всего текста |
| Инструкции | Узнать, как устроены задания и что ожидается от модели |
| Примеры входа и выхода | Понять формат задания |
| Язык и модальность | Узнать язык данных и их тип, например текст |
| Тип задачи | Понять ожидаемый формат ответа, например выбор варианта |
| Таксономия, навыки, теги | Найти испытания сходных способностей |
| Домены и поддомены | Определить предметную область, например транспорт → авиация |
| Размер и статистика длины | Оценить объём набора и размер заданий |
| Метрики | Узнать, какими показателями оценивается модель |
| Evaluation logic | Описание логики проверки ответа |
| Human baseline | Отдельный ориентир качества людей, если он известен |
| Ссылки и настройки адаптера | Найти данные, публикации и код интеграции |
| DatasetSubsample | Увидеть описанные части набора заданий |

Не все поля обязательно заполнены. Отсутствие результатов не означает, что Test ненастоящий: результат мог ещё не быть загружен. В стартовом наборе мы не придумывали числа для заполнения таблиц.

Число `0` в статистике не всегда можно уверенно интерпретировать как «в наборе нет заданий»: текущий контракт использует нулевые значения по умолчанию для не переданной статистики. Проверяйте описание и исходные данные, прежде чем делать выводы.

## 5. Чем Metric отличается от результата

**MetricDefinition** — описание показателя. Оно может существовать без Test и без результатов. Один и тот же показатель выбирают разные Test.

Например, Exact Match измеряет точное совпадение ответа с ожидаемым. Но то, как конкретный Test готовит ответы к сравнению и проверяет их, относится к его `evaluationLogic`, а не к глобальной записи Metric.

**MetricResult** — конкретное измерение:

```text
Один Test + одна Model + одна Metric + время получения → значение
```

Один Test может иметь несколько метрик, а одна модель — разные значения по ним. Система не складывает все эти показатели в единую «оценку модели».

Пример с вымышленными числами только для объяснения, не с реальными результатами нашего набора:

| Test | Модель | Metric | Значение |
| --- | --- | --- | --- |
| Испытание выбора ответа | Модель A | Exact Match | 0,82 |
| Испытание вызова инструментов | Модель A | Tool Call Accuracy | 0,75 |

Среднее этих двух чисел без дополнительных правил не является общим качеством модели. В нашем продукте такой расчёт не реализован.

**Human baseline** — справочный ориентир результата людей. Он хранится на Test отдельно. Это не искусственная модель с идентификатором `human`.

## 6. Что такое таксономия

Таксономия — просто организованный набор категорий, позволяющий классифицировать испытания. Она помогает не искать всё по тексту названия.

В проекте есть два важных дерева:

```text
MacroGroup — широкая группа способностей
└── SubGroup — более узкая группа внутри неё

Domain — предметная область
└── Subdomain — более узкая область
```

Примеры категорий не являются «умением самого каталога». Слово Reasoning в карточке описывает проверяемую способность модели, а Tools — особенности испытания. Каталог не становится агентом, который выполняет этот Test.

Остальные справочники — независимые списки: язык, тип задачи, модальность, сложность, capabilities и таксоны способностей. Их названия могут редактировать администраторы. `skills` и `abilityTags` — отдельные строковые списки, не таблицы тех же справочников.

Подробные правила связей — в [контракте предметной области](benchmark-domain-contract.md).

### Небольшой словарь ML-слов из карточек

| Слово | Что означает для читателя каталога |
| --- | --- |
| Input / output | Входное задание / ожидаемый ответ |
| Reasoning | Задания, требующие рассуждения, а не только воспроизведения факта |
| Tools | Испытание взаимодействия модели с инструментами, например выбором вызова функции |
| RAG | Сценарий, где модели дают найденные материалы для подготовки ответа |
| Few-shot | В задании есть несколько примеров нужного ответа |
| Long context | Вход содержит много информации; проверяется работа с ней |
| Exact Match | Показатель точного совпадения с эталоном; подготовка к сравнению задаётся Test |
| pass@1 / pass@k | Показатели успешности попыток, часто в задачах кода; точные правила зависят от Test |
| Baseline | Ориентир, с которым сравнивают результат |
| Evaluator | Внешний проверяющий механизм, применяющий правила оценки |

Эти слова описывают задачи и внешнюю оценку, а не функции, которые автоматически выполняет каталог. Для использования фильтров не нужно знать устройство нейросетей.

`medianSampleSizeWords` — типичная длина задания в словах. В requestLengthDist/responseLengthDist сохраняются минимум, медиана и максимум длины; это краткая статистика, не все исходные задания. Медиана — середина упорядоченного набора: половина значений находится по одну сторону, половина — по другую.

## 7. Зачем два бэкенда

### Benchmark Service — библиотека описаний испытаний

Он отвечает за группы Benchmark, конкретные Test и их DatasetSubsample. Хранит их в своей PostgreSQL и сообщает об изменениях.

Его можно использовать в другом проекте без нашего каталога: создавать и читать испытания через собственное HTTP API. Для этого не нужны пользователи, модерация, диалоги или БД каталога.

### Каталог — продукт вокруг этой библиотеки

Он отвечает за пользователей, справочники, метрики, результаты, публичную видимость, поиск, рекомендации, диалоги и аналитику.

Каталог получает копии описаний из Kafka, дополняет их своими справочниками и правилами публикации. Пользователь работает с одним UI и не обязан знать о разделении бэкендов.

Важно: независимость Benchmark Service не означает, что каталог может создавать Test без него. Запись выполняет Benchmark Service. Но ранее полученные карточки каталог способен читать из своей БД, пока сервис временно недоступен.

## 8. Kafka без специальных терминов

Kafka — система доставки сообщений между сервисами. Вместо вызова «создай Test прямо сейчас и ответь в этом же HTTP-запросе» каталог сохраняет просьбу создать Test и отправляет её через Kafka.

Benchmark Service выполняет просьбу в своей БД и возвращает сообщение с новым состоянием объекта. Каталог сохраняет эту копию и отмечает операцию как выполненную.

Это позволяет пережить временную недоступность второго сервиса. Но это не мгновенная общая транзакция между двумя БД: некоторое время каталог и сервис могут показывать разные состояния.

Потому HTTP `202 Accepted` означает **«просьба сохранена»**, а не **«Test уже создан»**. Интерфейс проверяет статус операции. При конфликте имён операция завершается ошибкой, даже если первая отправка вернула `202`.

## 9. Рекомендации — подбор, а не результат испытания

Пользователь описывает, что хочет проверить. Каталог:

1. Представляет текст запроса в виде числового описания его смысла — embedding.
2. Находит похожие описания Test в своём поисковом индексе.
3. Может уточнить порядок найденных карточек с помощью reranker.
4. Предлагает конкретный Test, который пользователь может выбрать или отклонить.

**Score рекомендаций** — насколько карточка подходит запросу. **MetricResult** — как модель справилась с испытанием. Это разные числа, они не заменяют друг друга.

В пользовательском сценарии сейчас выбирается один лучший кандидат. Если ничего не найдено, пустой результат считается нормальным завершением поиска, а не поломкой.

## 10. Зачем интервьюер и гипотезы

Интервьюер — внешний сервис, который ведёт уточняющий диалог при подготовке нового испытания. Каталог сохраняет историю и передаёт сообщения между ним и браузером.

Технически здесь два разных соединения:

- браузер ↔ каталог: Socket.IO;
- каталог ↔ интервьюер: WebSocket в режиме `AGENT_MODE=ws`.

Подбор существующих карточек выполняет сам каталог с поисковым индексом, embedder и reranker. Не нужно считать, что каждый поиск обязательно открывает новый сокет к интервьюеру или что рекомендации ходят через Benchmark Kafka topic.

Гипотеза — текстовое предложение, пришедшее в этом сценарии. Генерация гипотез — не запуск Test и не получение MetricResult. Также завершение разговора не означает автоматическую публикацию Test: подготовленную карточку ещё нужно отправить как заявку и пройти модерацию.

Подробнее: [рекомендации и интервьюер](recommendations-and-interviewer.md).

## 11. Чего в текущей версии нет

- Сущности и API Run.
- Запуска испытаний из каталога или Benchmark Service.
- Автоматического обучения моделей.
- Полного хранилища всех заданий Test внутри этих сервисов.
- Результатов отдельно на DatasetSubsample.
- Единого общего score из нескольких Metric.
- Полноценной истории опубликованных TestVersion и ModelVersion.

`aggregateVersion` в сообщении — служебный счётчик изменений записи. Это не сохранённая версия экзамена, которую можно выбрать и выполнить повторно.

Если у Test уже есть результаты, изменять или удалять его описание сейчас нельзя: иначе старое число относилось бы к другим правилам проверки. Для снятия этого ограничения нужна будущая модель версий, не ручное отключение проверки.

## 12. Частые вопросы

### Почему Test есть в Benchmark Service, но его нет на главной странице?

Нужно дождаться сообщения об изменении, а затем проверить наличие CatalogEntry и её состояние. Только опубликованные и не удалённые Test попадают в публичные карточки. Создание через собственное API Benchmark Service само по себе не создаёт решение о публикации в каталоге.

### Почему автор видит карточку, а другой пользователь — нет?

Автор может видеть свои заявки, включая `validation` и `rejected`. Публичный каталог эти состояния скрывает.

### Можно ли использовать один DatasetSubsample в разных Test?

Нет. Он принадлежит конкретному Test. Не стоит использовать его как отдельный переносимый Dataset.

### Почему в каталоге есть копия Test, если мы вынесли его из монолита?

Копия нужна для чтения, поиска и фильтров. Она не заменяет владельца описания. Каталог не редактирует эту копию как источник данных: он посылает команду Benchmark Service и ждёт обновления.

### Две БД должны стоять на разных серверах?

Не обязательно. Локально они могут работать на одном компьютере. Важно, что сервисы имеют отдельные базы и не обращаются к таблицам друг друга.

### Тесты проекта зелёные — значит, ошибок больше не будет?

Нет. Автоматические проверки дают уверенность в конкретных сценариях. Они не доказывают отсутствие всех ошибок и не заменяют проверки настоящих внешних сервисов и нагрузки. [Инструкция тестирования](testing.md) объясняет, какие проверки что доказывают.
