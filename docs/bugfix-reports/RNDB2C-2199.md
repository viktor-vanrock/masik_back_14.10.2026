# RNDB2C-2199 — понятная ошибка при занятом email или имени

Дата проверки: 28 октября 2026 года. Backend: ветка `codex/conference-catalog-bugfixes`.

До исправления регистрация нового username с существующим email нарушала уникальность в БД и возвращала `500 Internal server error`. Теперь создание и обновление пользователя возвращают `409` с указанием поля. Повторная запись не создаётся, неудачное обновление сохраняет прежние данные.

```json
{
  "statusCode": 409,
  "code": "EMAIL_ALREADY_EXISTS",
  "message": "Пользователь с таким email уже зарегистрирован.",
  "field": "email"
}
```

Для занятого имени: `USERNAME_ALREADY_EXISTS`, поле `username`, сообщение «Это имя пользователя уже занято.». Контракт одинаков при предварительной проверке и при конфликте одновременных записей. Технические сведения БД не попадают в ответ. Неизвестные ошибки не преобразуются в конфликт пользователя.

Исправление ограничено `UsersService` и одной наследуемой от Nest `ConflictException` ошибкой. Для Prisma 7 PostgreSQL адаптер хранит нарушенное поле в `meta.driverAdapterError.cause.constraint.fields`; поддерживается также `meta.target`.

## Автоматическая проверка

Из корня backend после установки зависимостей:

```sh
DB_URL=postgresql://qa:qa@127.0.0.1:1/unused npm run prisma:generate
npm run test:unit -- --runTestsByPath src/users/users.integration.spec.ts
npm run typecheck
npx eslint src/users/users.service.ts src/users/user-already-exists.exception.ts src/users/users.integration.spec.ts
```

`prisma:generate` создаёт локальный клиент из схемы и не подключается к указанной БД. В тестах применяется настоящий Prisma Client + PrismaPg с PostgreSQL PGlite в памяти. SQL таблицы и уникальных индексов взят из миграции; общая БД не используется.

Результат: **12 тестов прошли**, typecheck и ESLint прошли. Проверены email и username, одновременная регистрация, конфликты обновления, сохранность данных, успешная регистрация с HttpOnly-cookie, хеширование пароля и сохранение неизвестных ошибок.

## Повторная проверка через фронт

Запустить отдельный сервер из корня backend:

```sh
node scripts/qa/conference-auth.cjs
```

Он слушает только `127.0.0.1:3189` (порт меняется через `QA_AUTH_PORT`). Использует настоящие контроллеры, сервисы, репозиторий, валидацию и Origin/JWT/Role guards. Данные находятся только в памяти и сбрасываются при перезапуске. Дополнительный доступный только в этом скрипте `GET /__qa/users` показывает тестовые id/username/email для проверки количества записей. Обращения к внешней БД отключены; интерактивные транзакции не поддерживаются, для сценариев регистрации они не требуются.

Начальная запись: username `existing-user`, email `existing@example.test`, тестовый пароль `BenchFactory2026!`.

Открыть локальный фронт на `http://127.0.0.1:5178`, направив `/api/auth/*` и `/api/users/profile` на этот сервер через прокси или браузерный QA-сценарий, затем:

1. На регистрации ввести новый username и `existing@example.test`: сообщение возле email, Network → `409` и `EMAIL_ALREADY_EXISTS`; `/__qa/users` всё ещё содержит одну запись.
2. Ввести `existing-user` и новый email: сообщение возле имени, `409` и `USERNAME_ALREADY_EXISTS`; число записей не изменилось.
3. Ввести уникальные username и email: `201`, успешная авторизация, `/api/users/profile` возвращает нового пользователя; число записей увеличилось на один.

Скриншоты «до/после» и проверка формы находятся в `benchmark-catalog-front/docs/bugfix-reports/2026-10-28/screenshots/`: `registration-before.png`, `registration-after.png`, `registration-username-after.png`, `registration-success-after.png`.

Проверка использует изолированное локальное окружение. Развёртывание и повторная проверка на DEV выполняются отдельно; сервисы Factory в этом сценарии не участвуют.
