# GitLab CI/CD

| Событие | Автоматические проверки | Публикация образа | Деплой |
| --- | --- | --- | --- |
| Открытие или обновление MR в `develop` | Сборка, ESLint, тесты | Нет | Нет |
| Открытие или обновление MR в `main` | Сборка, ESLint, тесты | Нет | Нет |
| Коммит в `develop` | Сборка, ESLint, тесты | После успешных проверок | Только вручную на dev |
| Коммит в `main` | Сборка, ESLint, тесты | После успешных проверок | Только вручную на prod |

Другие ветки без подходящего MR и теги не создают pipeline. Для feature-веток нет дублирующего push pipeline. Pipeline ветки `develop` сохраняется и при открытом MR из неё в `main`, чтобы можно было вручную выкатить проверенный dev-образ.

Тестовая задача выполняет `npm run test:unit -- --ci` (Jest, последовательно). Ошибки сборки, линта или тестов делают pipeline неуспешным; отсутствие тестов тоже считается ошибкой. Для запрета слияния при красном pipeline в настройках проекта GitLab должна быть включена **Pipelines must succeed**.

Prisma генерируется отдельной задачей на `kube-stage`; generated client и зависимости передаются сборке и проверкам через artifacts. PostgreSQL e2e и проверки живой Kafka не входят в этот pipeline: порядок их запуска описан в [testing.md](testing.md).

После успешного branch pipeline нужный deploy job запускается кнопкой **Play**. Ручные задачи необязательны для зелёного pipeline; сам pipeline никогда не выкатывает стенд автоматически. Dev и prod сохраняют свои runner tags, namespace и Helm values из `.deploy.yml`. Это правило распространяется и на Redis-задачи, если они есть в репозитории.

GitLab читает конфигурацию из исходной ветки MR. Уже открытые feature-ветки со старым `.gitlab-ci.yml` нужно обновить из целевой ветки после слияния настроек CI, затем запустить новый MR pipeline.
