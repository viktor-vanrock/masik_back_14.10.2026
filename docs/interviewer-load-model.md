# Нагрузочная модель рекомендаций и Interviewer

> **Дополнительные технические материалы.** Общую картину текущих двух сервисов и практические ограничения смотрите в [новом руководстве](recommendations-and-interviewer.md). Этот файл сохраняет детали отдельного модуля; при противоречии с текущими маршрутами/границами ответственности используйте новое руководство и код.

**Дата фиксации:** 2026-09-05

## Два независимых контура

Socket.IO между браузером и Catalogue не означает, что любая рекомендация
создаёт WebSocket до Interviewer.

1. Поиск существующего Test выполняется через HTTP-цепочку
   `embedder -> pgvector -> reranker`. Socket.IO только доставляет браузеру
   подтверждение и итог.
2. Создание нового Test — интерактивный диалог. Только после
   `reject_recommendation` или `start_benchmark_creation` Catalogue открывает
   отдельный исходящий WebSocket до Interviewer.

Следовательно, `N` одновременно активных диалогов создания означают `N`
исходящих WS-соединений на Catalogue и `N` соединений на Interviewer. Сами
открытые сокеты обычно дешевле ML-генерации; фактический предел чаще задают
очередь/воркеры Interviewer, память, file descriptors и PostgreSQL-записи
ответов.

## Поведение Catalogue при перегрузке

Ограничения задаются на один процесс/pod:

| Переменная | Default | Назначение |
| --- | ---: | --- |
| `AGENT_MAX_ACTIVE_SESSIONS` | 200 | максимум активных исходящих Interviewer WS |
| `AGENT_MAX_PENDING_MESSAGES_PER_SESSION` | 32 | максимум сообщений до открытия/reconnect WS |
| `AGENT_MAX_BUFFERED_BYTES_PER_SESSION` | 1 MiB | общий предел pending/native send buffer |
| `AGENT_MAX_PAYLOAD_BYTES` | 1 MiB | максимум одного входящего или исходящего WS payload |
| `AGENT_SESSION_IDLE_TIMEOUT_MS` | 30 min | закрытие забытой сессии без активности |
| `RECOMMENDATION_MAX_CONCURRENT_EXECUTIONS` | 16 | параллельные HTTP recommendation pipeline |

- До лимита каждая create-сессия получает собственный WS и heartbeat.
- Следующая сессия сверх лимита отклоняется сразу с явной ошибкой и предложением
  повторить позже, а не попадает в бесконечную очередь.
- Сообщения во время connect/reconnect буферизуются только в заданных пределах.
  Переполненный buffer/backpressure даёт явную ошибку.
- Обрыв соединения запускает ограниченный exponential reconnect. После
  исчерпания попыток браузер получает финальную transport error, а ресурсы
  сессии освобождаются.
- Ответы одного conversation сохраняются строго последовательно. Повторная
  привязка браузера заменяет старый listener и не умножает обработку ответа.
- Recommendation pipeline сверх отдельного лимита сохраняется как
  `RECOMMENDATION_OVERLOADED`, `retryable=true`; embedder/reranker не вызываются.

Defaults — защитные предохранители, а не доказанная производительность. В
production лимиты следует выставлять по меньшему из двух измеренных значений:
безопасная ёмкость одного Catalogue pod и выделенная ему ёмкость Interviewer/ML
endpoint.

Число входящих browser Socket.IO connections пока ограничивается ingress/OS, а
не отдельным application-level лимитом. Само соединение не запускает ML, но для
production всё равно нужны connection/rate limits на ingress. В коде доступны
load snapshots сервисов, однако следующим operational шагом их нужно вывести в
Prometheus/общую систему метрик и алертов.

## Нужна ли Kafka

Для пошагового диалога WebSocket подходит: пользователь и Interviewer обмениваются
вопросами и ответами в реальном времени. Kafka сама по себе не уменьшит число
активных диалогов и не решит backpressure без admission control.

Очередь сообщений нужна, если workflow превращается в долговечную фоновую job:
запрос можно принять, пережить рестарт браузера/процесса, выполнить позже и
доставить результат независимо от текущего сокета. Тогда Kafka/RabbitMQ/другая
durable queue может быть транспортом job/event, а Socket.IO остаётся каналом
уведомлений. Это отдельный протокол, а не простая замена текущего WS.

Текущее создание остаётся интерактивным и недолговечным: disconnect браузера
закрывает исходящий Interviewer WS. История в PostgreSQL позволяет восстановить
диалог, но незавершённая генерация внешнего сервиса не является durable job.

## Что проверено автоматически

Unit-тесты фиксируют:

- admission limit активных сессий и recommendation pipeline;
- bounded message/byte buffer и native WS backpressure;
- максимальный размер payload;
- idle cleanup и terminal error;
- отсутствие накопления listeners;
- последовательную запись быстрых ответов;
- ограниченный reconnect и восстановление `init/history`.

Concurrent smoke-тест создаёт 32 независимых session lifecycle и проверяет
полную очистку без сетевых допущений тестовой среды. Он ловит ошибки управления
сессиями, но не заменяет нагрузочное испытание реального Interviewer.

## Что измерить на стенде

Прогонять ступени, например `10 -> 25 -> 50 -> 100 -> 200` одновременных
диалогов и отдельно recommendation pipeline. На каждой ступени фиксировать:

- p50/p95/p99 времени connect, первого вопроса и полного ответа;
- долю ошибок, reconnect и overload;
- RSS/heap, event-loop lag и количество file descriptors Catalogue;
- занятость пула PostgreSQL и latency записи сообщений;
- очередь, GPU/CPU/RAM и лимиты генерации Interviewer, embedder и reranker.

Без такого прогона нельзя честно утверждать, что сервис выдержит конкретное
число пользователей. Код теперь деградирует контролируемо, но численная ёмкость
определяется только на целевой инфраструктуре.

## Горизонтальное масштабирование

Сессии и их callbacks пока находятся в памяти процесса. Для нескольких
Catalogue pod нужны sticky routing для Socket.IO и распределённое владение
conversation (lease/lock), чтобы два pod не открыли два Interviewer WS для одной
беседы. Суммировать `AGENT_MAX_ACTIVE_SESSIONS` по pod можно только после этого;
ёмкость внешнего Interviewer при этом всё равно остаётся общим верхним пределом.
