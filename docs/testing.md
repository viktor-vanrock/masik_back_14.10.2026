# Тестирование: что проверяется и как не потерять данные

Актуально после разделения, 16.09.2026. Здесь описаны команды, а не обещание стопроцентного отсутствия ошибок.

## 1. Уровни проверки

| Уровень | Простое объяснение | Чего не доказывает |
| --- | --- | --- |
| Unit | Правило или компонент с подменёнными зависимостями | Работа реальных БД, Kafka и внешних моделей |
| Integration / e2e с БД | Настоящие транзакции, ограничения, HTTP-сценарии | Полная доставка между двумя отдельно запущенными сервисами |
| Kafka e2e источника | Настоящий брокер и обработка команды/ответа | Все сценарии UI каталога |
| Topology smoke | Catalog → Kafka → Benchmark Service → Kafka → Catalog | Полное покрытие всех сценариев и нагрузки |
| UI + Postman | Поведение для пользователя, реальные запросы | Все редкие ветки и долгосрочную надёжность |
| Нагрузочная проверка | Задержки и ресурсы на выбранном числе пользователей | Универсальный предел для любого окружения |

## 2. Сначала правило безопасности

**Рабочие БД benchmark_catalog и benchmark_service не являются тестовыми.**

Каталоговый runner сбрасывает выбранную тестовую БД через migrate reset --force. Он проверяет, что её имя содержит test, но не способен определить ценность лежащих там данных.

У Benchmark Service **нет аналогичной проверки имени БД в e2e-команде**. Его тестовая настройка по умолчанию может указать на обычную локальную benchmark_service, а e2e очищают таблицы. Поэтому для его e2e и Kafka e2e обязательно задавайте DB_URL явно на отдельную одноразовую БД, например benchmark_service_test.

Не полагайтесь на название команды `test` как на гарантию безопасного подключения.

## 3. Команды каталога

В `benchmark-catalog-back`:

```bash
npm run lint
npm run typecheck
npm run test:unit
npm run test:cov -- --runInBand
npm run seed:catalog:test
npm run build
```

Полный прогон с существующей **одноразовой** PostgreSQL + pgvector:

```bash
TEST_DATABASE_URL='postgresql://benchmark_catalog_test:benchmark_catalog_test@127.0.0.1:55432/benchmark_catalog_test?schema=public' \
  npm run verify
```

verify включает lint, обе проверки типов, unit, e2e и build. При TEST_DATABASE_URL отдельная инфраструктура не создаётся и не останавливается, но данные этой БД **сбрасываются**.

Если TEST_DATABASE_URL не передан, `npm run test:e2e` использует уже имеющуюся локальную тестовую обвязку: запускает отдельный PostgreSQL/pgvector, применяет миграции после сброса, запускает Jest и убирает тестовый контур. Это не production/Docker build workflow; можно вместо него использовать указанный выше явный URL без запуска контейнеров.

Дополнительные параметры:

- BENCHMARK_TEST_DB_PORT — порт автоматически управляемой тестовой БД, по умолчанию 55432.
- KEEP_TEST_DATABASE=true — оставить управляемый тестовый контур для отладки.
- Аргументы Jest можно передать после `--`.

Один файл:

```bash
TEST_DATABASE_URL='postgresql://benchmark_catalog_test:benchmark_catalog_test@127.0.0.1:55432/benchmark_catalog_test?schema=public' \
  npm run test:e2e -- --runTestsByPath test/benchmark-remote-write.e2e-spec.ts
```

Прямой `test:e2e:jest` обходит создание/проверку БД runner. Не используйте его с окружением рабочего приложения.

Runner задаёт NODE_ENV=test, тестовые секреты, mock для интервьюера/embedding/reranker, Kafka=false, admin seed=false. Бизнес-логику, создание Outbox и применение событий проверяют тесты; живую межсервисную доставку проверяет отдельный topology smoke.

### Что искать в существующих e2e

| Файл / группа | Что защищает |
| --- | --- |
| benchmark-remote-write, benchmark-command-status | 202, команды, права на операции, подтверждение/отказ |
| benchmark-projection-reads, benchmark-test-projection-reads | Чтение копий и публичные/административные ограничения |
| catalog-benchmark-projection, catalog-entry-projection-boundary | События, версии, модерация и граница владельцев |
| metric-result-projection-boundary, metrics | Назначения, блокировка после результата, модели/метрики |
| taxonomy, taxonomy-projection-usage | Родительские связи и защита используемых справочников |
| outbox-leasing | Конкурирующая отправка и временное владение строками |
| search-projection-boundary | Поиск и публичная область данных |
| external-benchmark-projection | Внешние представления карточек |
| conversation-ownership, conversation-actions-idempotency | Чужие беседы, повторы и конфликтующие решения |
| analytics-projection-boundary, metric-upload-row-boundary | Стабильные внешние ID и ограничения импортных данных |

В таблице опущен общий суффикс `.e2e-spec.ts`. Unit расположены рядом с production-кодом в src, включая отдельные tests-каталоги.

Coverage gate — нижняя защита от регресса, **не 100% покрытия проекта**. Он считает не все файлы: generated Prisma, часть DTO, контроллеров и wiring исключены. Их поведение проверяется также HTTP/e2e и типизацией. Не снижайте пороги только ради зелёного результата.

## 4. Проверки Benchmark Service

В его репозитории:

```bash
npm run verify
```

Эта команда включает lint, typecheck, unit и build, **но не e2e**.

Получите/создайте отдельную БД benchmark_service_test. Затем явно примените миграции и запустите:

```bash
DB_URL='postgresql://benchmark_service:benchmark_service@127.0.0.1:55433/benchmark_service_test?schema=public' \
  npm run db:migrate

DB_URL='postgresql://benchmark_service:benchmark_service@127.0.0.1:55433/benchmark_service_test?schema=public' \
  KAFKA_ENABLED=false npm run test:e2e

DB_URL='postgresql://benchmark_service:benchmark_service@127.0.0.1:55433/benchmark_service_test?schema=public' \
  KAFKA_BROKERS=127.0.0.1:19092 npm run test:kafka:e2e
```

Здесь применяется **DB_URL**, не каталоговая переменная TEST_DATABASE_URL. Команды очищают тестовые данные. Не запускайте их параллельно на одной БД.

Kafka-прогон использует уникальные топики и consumer group конкретного запуска; не должен подменять рабочий поток каталога. Тесты покрывают формат сообщений, дубликаты, версии, ошибки/DLQ, Outbox и доменные правила. Подробности — в документации самого сервиса.

## 5. Сквозная связка и UI

После запуска обычных локальных приложений и Kafka:

```bash
npm run benchmark:topology:smoke
```

Это команда **каталога**, которая создаёт и мягко удаляет свои временные группы/Test. Она не запускается на одноразовой e2e-БД вместо рабочих локальных серверов: ей нужны настоящие HTTP-адреса двух приложений. Используйте только разрешённое локальное окружение и SuperUser.

Frontend отдельно:

```bash
npm test
npm run build
```

Затем живой проход по [процессам приёмки](business-processes.md#9-что-проверять-при-приёмке) и коллекциям `postman/`. Для экспериментов используйте уникальные имена, не исходные 40 карточек.

## 6. Как добавлять тесты дальше

1. Сначала описать ожидаемое правило и corner case, а не копировать текущее ошибочное поведение.
2. Unit — чистые преобразования, условия отказа и переходы состояний.
3. БД/e2e — транзакции, права, публичная видимость и сохранность данных.
4. Kafka e2e — повторы доставки, рестарт, старые события, зависшая отправка и DLQ.
5. Отдельно проверить, что частичный PATCH не очищает неуказанное.
6. Для каждого сбоя проверять не только код ответа, но и отсутствие частичных/лишних записей.
7. Не привязывать тест к наполненности рабочего каталога или порядку предыдущих прогонов.

Реальные модельные сервисы, VPN, реальная нагрузка и особенности размещения проверяются отдельно. При обновлении только документации полный функциональный прогон сам по себе не заменяет сверку текста с кодом.
